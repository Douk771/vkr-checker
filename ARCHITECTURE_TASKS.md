## 1. Принципы параллельной работы

- **Контракт заморожен на старте.** `api/openapi.yaml` — источник истины. Менять его можно только PR-ом, где одновременно правятся схема, Pydantic-модели и мок-фикстуры. Если меняется форма отчёта, повышается `schema_version` (API_CONTRACT §6).
- **Frontend не ждёт backend.** Фронтенд работает против `prism mock api/openapi.yaml` и golden-JSON из `tests/golden/`. Первые три golden-JSON пишутся **вручную** в X-01 и валидируются jsonschema. Позже их заменяют реальные выходы бэкенда.
- **Backend внутри себя распараллеливается по слоям** (A §3, правило зависимостей). Пока `docx/` не готов, `checks/` разрабатываются на фикстурах-моделях: `Document`, собранный в тесте через фабрику `tests/fixtures/model_factory.py`, без .docx.
- **Ветки и мерджи** ведёт devops-engineer. Задачи нарезаны так, чтобы каждая была отдельным PR размером ≤ ~1 дня ревью.
- **Публичный репо:** в коде, тестах и фикстурах нет дословных цитат требований и реальных фамилий (SPEC §0 п.5). Это входит в DoD каждой задачи.

## 3. Синтетические тестовые .docx (X-02, владелец — backend)

Решение заказчика §0 п.3: калибровка и тесты только на синтетике. Фикстуры **генерируются кодом**, в репо лежат только генераторы (`tests/fixtures/builders/`), результат — в `tests/fixtures/generated/` (в `.gitignore`). `scripts/build_fixtures.py` собирает всё, pytest-фикстура собирает лениво с кэшем по хэшу генератора.

**Устройство.**
- `builders/base.py` — `ThesisBuilder`: fluent-API поверх python-docx (`title_page()`, `toc(field=True|False)`, `intro(elements=...)`, `chapter(n, role, subsections=[...])`, `table(rows, caption, style=...)`, `figure(caption)`, `conclusion()`, `bibliography(n)`, `appendix(key)`), детерминированный: фиксированные `core.xml` даты, без случайности (seed, если нужен объём текста).
- `builders/xml_patch.py` — lxml-патчи для того, чего python-docx не умеет: `numbering.xml` (многоуровневые списки, заголовки с нумерацией через стиль), условные стили таблиц (`tblStylePr`, `tblLook`, `cnfStyle`), поля `SEQ`/`REF`/`TOC`/`PAGEREF` с устаревшим результатом, рецензирование (`w:ins/w:del/w:moveFrom/To`), надписи с рисунком и подписью, `mc:AlternateContent`, `sectPr` разделов, `exact`-высота строк, ссылка на несуществующий стиль таблицы.
- `builders/text.py` — генератор нейтрального псевдо-научного текста (свой словарь, вымышленные фамилии вида «Иванова А.А.» из фиксированного списка, без фрагментов методички) с управляемым объёмом в страницах.
- `builders/variants.py` — мутации эталона: `clean()` и по одной мутации на каждый пункт правила (`missing_section("CONCLUSION")`, `table_indent(origin="para_style")`, `percent_sum(103)`, `sample_mismatch(30, 32)`, …).

**Набор (минимум).**
| Фикстура | Назначение |
|---|---|
| `clean_70p` | эталон: ~70 стр., все разделы, 2 главы, 6 таблиц, 3 рисунка, приложения → 0 Н, 0 П |
| `clean_150p` | бюджет производительности (B-72) |
| `rule_<ID>_<case>` | пара «чистая/с ошибкой» на каждое правило C §4 (SPEC §4); ~60 файлов |
| `parse_*` | XML-крайности для B-11..B-15: стили, нумерация, поля, правки, надписи, вложенные таблицы |
| `layout_*` | таблица на 2 стр., короткая таблица на стыке страниц, устаревшие номера в оглавлении, приложение без разрыва, незнакомый шрифт |
| `bad_*` | .doc/.pdf/.odt с подменённым расширением, зашифрованный, zip-бомба, пустой, 21 МБ |
| `diff_v1/v2_<case>` | пары версий на DIF-01..06: переименование раздела, перемещение абзаца, смена N, удалённый метод, перенумерация таблиц, изменённые ячейки при неизменных выводах |

Ожидаемые результаты для `rule_*` и `diff_*` записываются рядом с генератором (`expected = {"TBL-01": "violation", ...}`) — тест проверяет уровень, а golden (B-70) — полный JSON для 3–5 ключевых файлов. Пагинационные фикстуры проверяются на допуск `PAGE_TOLERANCE`, а не на точную страницу.

## 6. Definition of Done (для каждой задачи)

- Тесты на синтетике; для правила — пара «чистая/с ошибкой», эталон `clean_70p` остаётся 0 Н / 0 П.
- Контракт: backend-тест `tests/contract` зелёный; frontend рендерит все golden без ошибок в консоли.
- Детерминизм: два прогона дают одинаковый JSON (кроме `checked_at`).
- Нет текста работ в логах; temp-файлы удалены; нет цитат требований и реальных фамилий.
- Пороги — только в `thresholds.py`.

## 8. Открытые вопросы к человеку (product-analyst / заказчик)

1. **STR-06 и TBL-12** — новые ID для проверок, которые решение §0 п.1 перевело из NC-01 в код (C §4). Подтвердить ID и уровень «только подозрение».

3. **BIB-01 (US-25, Could)** — включать в MVP или отложить.
4. **Целевая машина для замера** (B-20): ноутбук заказчика (ОС, ОЗУ)? От этого зависит выбор `soffice` vs `unoserver`.
